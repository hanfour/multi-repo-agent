## 觸發訊號
diff 裡新增或修改了一個條件判斷（`if (x)`、`x && …`、`x ? … : …`、`!x` 早退、或用 `||` 給預設值），而 `x` 的來源是：使用者輸入欄位、資料庫讀出的值、聚合/計算結果（count/sum/avg/rating/score/index）、或外部設定值——且該欄位型別上允許 `0`、`false`、`''`、`NaN`、空陣列這類「合法但為假」的值。看到這種條件時，要去確認：這個欄位在業務語意上，`0`／`false`／空字串是不是一個「有意義、需要被處理」的值，而不是「沒有提供」。

## 判準
`if (x)` 這種寫法沒辦法區分「使用者明確給了假值」和「使用者根本沒給值」，兩者會走進同一個分支。當這個欄位的假值本身就是合法業務資料（例如評分 0 分、數量 0 筆、旗標 false、允許空字串的訊息欄位）時，程式會把一筆真實資料當成缺值處理，而且通常不會拋錯——資料只是被悄悄丟掉或走錯分支，等到有人抱怨「為什麼我的資料不見了」才會被發現。這類問題無法靠型別檢查抓出來（`x` 的型別是對的，只是值恰好是假值），只能靠讀懂欄位語意判斷。同樣的risk也出現在跨實作/跨環境的行為對齊上（例如兩個 HTTP adapter 對「送出假值 body」的處理不一致）：diff 改了其中一邊的判斷邏輯時，要確認假值輸入在所有相關路徑上的行為是否一致、是否符合預期。

## 嚴重度
CRITICAL：假值代表的資料被靜默遺失且不可逆（寫入被跳過、使用者提交的資料沒有送出、且系統認為流程已完成不會再重試/再詢問）。
HIGH：假值輸入導致邏輯走錯分支或行為在不同 adapter／環境間不一致，可被外部觀察到，但不會直接遺失持久化資料。
MEDIUM：假值誤判只影響內部中介狀態或極少被觸發的 edge case，且有其他機制（重試、後續步驟）可以補救。

## 反例（不該報）
- 該欄位型別本身不可能是 falsy（例如已在更上層驗證過的非空 UUID 字串、非 nullable 的物件參照），此時 truthy check 沒有陷阱。
- 程式碼已經用 `!== undefined`、`?? `、`in` 或明確的 `null`/`undefined` 檢查來排除「未提供」和「合法假值」的歧義，這正是這條規則想要的寫法，不該再報。
- 該欄位語意上假值本身就等於「無」（例如錯誤訊息欄位空字串就代表沒有錯誤、選填的 label 空字串就代表沒有標籤），此時用 truthy check 判斷「有沒有值」是正確設計，不是漏洞。
