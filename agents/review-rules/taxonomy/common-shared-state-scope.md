## 觸發訊號

diff 出現以下任一種變更時，要去確認：這個狀態的生命週期跟它現在寄居的作用域是否匹配。

- 新增或修改一個模組層級 `let`/`var`、class 的 `static` 欄位，或任何在函式呼叫之間存活的變數，用來在呼叫之間傳遞資訊（尤其是原本可以用參數/回傳值傳遞、但因為「不好整條路徑穿參數」而改用全域變數的情況，如全域 stack/counter/flag）。
- 新增一段程式碼，把計算結果寫回一個「本次呼叫不是唯一擁有者」的共享物件上（例如寫進一個被多個呼叫端共用的 cache 物件、一個被多個 test/request 重複使用的物件、一個 singleton 的欄位），且沒有在旁邊看到對應的失效（invalidation）或作用域邊界重置邏輯。
- 新增或修改一個函式簽章，把「只對當下這次呼叫/這個檔案有效的設定」跟「對整個 program/session 都有效的設定」混在同一個沒有區分作用域的參數或欄位裡（例如同時可能收到 per-file options 或 global compilerOptions，卻只用一個籠統的名字如 `options`）。
- 測試或 baseline 的輸出依賴於一個外部共享狀態（例如作業系統層級的 cache、跨測試共用的目錄/inode），而不是只依賴這個測試自己準備的輸入。

## 判準

問題不在「這一行邏輯錯了」，而在「這份狀態被放在了比它實際生命週期更寬的作用域」。當狀態被提升到呼叫者看不見的地方時，正確性就開始依賴一個沒有寫在程式碼裡、也沒人強制檢查的隱含假設：這個狀態會在對的時間點被重置、不會被巢狀/併發/重入的呼叫互相污染、也不會在它依賴的輸入改變後仍然殘留舊值。resident reviewer 要做的判斷是：這個共享點是不是真的預期被多方共用（那就沒問題），還是只是圖方便而把本該局部的東西搬到了外面——一旦搬出去，兩層呼叫之外的人完全不知道這份狀態存在，也就沒辦法判斷它何時是舊的、何時會被別的呼叫悄悄改掉。

## 嚴重度
CRITICAL：共享狀態會讓本該互相獨立的操作互相污染出錯的結果——例如一個巢狀/遞迴呼叫寫入的全域狀態，外層或平行的呼叫沒有清掉就接著讀到，導致算出錯誤答案；或是快取寫進共享物件後，永遠不會在它依賴的輸入改變時失效。

HIGH：目前沒看到具體壞掉的案例，但共享狀態的安全性完全建立在「現在還沒有人巢狀呼叫/重入/並發呼叫這段程式碼」這個未被強制的假設上——一旦未來有人這樣呼叫，就會壞，而且沒有任何機制阻止那種呼叫方式出現。

MEDIUM：共享狀態只會拖慢除錯或造成測試互相干擾（例如測試輸出依賴另一個測試留下的全域快取/檔案系統狀態），還沒有觀察到生產路徑上的正確性問題。

## 反例（不該報）
- 真正被設計成 process-wide/session-wide 的單例狀態（例如全域設定、feature flag），本來就預期被所有呼叫端共用，沒有「應該局部化」的期待。
- 宣告在函式/方法內部的區域變數，即使該函式被呼叫很多次——因為每次呼叫都重新配置，並不構成「共享」。
- 有快取，但快取鍵已經涵蓋了所有會影響快取值的輸入，且輸入改變時會正確失效——這是設計良好的快取，不是本規則要抓的問題。
