## 觸發訊號
diff 中新增或修改的宣告/命名出現以下任一情況：
- 用 `let` 宣告一個變數，但在該變數的完整作用域內（含 diff 前後既有程式碼）都沒有被重新賦值，應改為 `const`
- 新增的內部/未匯出 class、interface 用底線前綴命名（如 `_ComputedRef`），而不是用能表達語意的名稱（如 `ComputedRefImpl`）
- 新增的字串常數／訊息內容，重複了呼叫端函式已經自動附加的前綴或格式（例如 `warn()` 本身就會加 `[Vue warn] `，字串字面量裡又手動寫一次 `[Vue warn] `）
- 新增/修改的測試描述（`test(...)` / `it(...)` 的命名關鍵字、描述文字風格）與同一檔案裡既有測試案例的慣例不一致

## 判準
這四種情況本質上都是「讓後續維護者對程式碼語意產生錯誤預期」的一致性問題：`let` 沒有被重新賦值會誤導讀者以為之後有變動、要多想一層；底線前綴命名沒有實質意義卻讓人聯想到私有/危險 API，語意不明確；重複的訊息前綴會在最終輸出裡出現兩次同樣字樣，讀起來冗贅甚至像 bug；測試命名不一致會讓同一檔案讀起來像出自不同慣例的補丁，增加日後 grep/理解成本。這些都不影響執行期正確性，但都會增加 reviewer 與未來維護者的認知負擔，是資深 reviewer 會順手挑出來的「順手清一下」類意見。

## 嚴重度
CRITICAL：不適用（此類問題不涉及執行期錯誤、資料損毀或安全風險）。
HIGH：不適用；若底線前綴的內部 class 被意外匯出成公開 API，使用者可能誤判其為私有實作而依賴不穩定介面，此情況應升級處理但仍非本規則核心。
MEDIUM：命名或格式不一致的對象位於公開 API 表面（匯出的型別、對外可見的錯誤訊息）而非純內部實作細節。

## 反例（不該報）
- `let` 宣告的變數雖然在 diff 片段裡看不到重新賦值，但在同函式其他分支、迴圈或 callback 中確實有被賦值——需確認完整作用域再判斷，不能只看 diff hunk。
- 底線前綴是專案既有、一致採用的「內部/私有」命名慣例（整個檔案或模組都用 `_` 標示非公開成員），此時前綴本身就是有意義的語意標記，不該要求改名。
- 新檔案第一次建立測試案例，該檔案本身尚無既定的 `test`/`it` 慣例可比對，此時命名選擇是合理的起點，不算不一致。
- 字串前綴重複是刻意的防禦性寫法（例如訊息之後可能被抽出、脫離自動加前綴的呼叫路徑，先寫完整字串是有意識的權衡），而非單純疏忽。
