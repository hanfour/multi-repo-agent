## 觸發訊號
diff 裡新增或修改了下列任一種命名情境：
- 新增的型別/介面/選項物件名稱與既有同類型名稱僅有極小差異（例如單複數：`ChangeNodeOptions` vs `ChangeNodesOptions`），且兩者會同時存在於呼叫端 API 中。
- 測試檔案裡新增的 test case 直接複製貼上了另一個既有測試的名稱（或高度相似的名稱），但測試內容其實驗證的是不同情境。
- 編譯器/框架內部生成的佔位名稱（如 `__computed`、`arg_0`、autogenerated symbol）被直接寫進使用者可見或會被序列化/持久化的輸出（錯誤訊息、型別顯示字串、baseline/snapshot、對外 API 回應）。

## 判準
- 名稱只差一兩個字元（尤其單複數）時，呼叫端很容易選錯、review 時也難以一眼分辨兩者語意差異，是典型的「看起來對但其實錯」bug 來源。
- 複製貼上的測試名稱會誤導未來維護者對「這個測試在驗證什麼」的理解，導致真正該覆蓋的情境其實沒被測到（silent coverage gap），比完全沒有測試更危險，因為它會製造虛假的信心。
- 內部/生成的佔位名稱一旦出現在對外輸出，就會被其他程式碼或使用者無意間依賴（parse 它、比對它），變成一個從未被設計成穩定契約的意外契約；日後只要內部實作變動，這個輸出就會悄悄壞掉且難以追查原因。

## 嚴重度
CRITICAL：內部生成/佔位名稱洩漏到會被持久化或被其他程式解析依賴的輸出（例如序列化格式、snapshot baseline、對外 API response），一旦有人依賴它就形成隱性契約。
HIGH：測試名稱因複製貼上而與其他測試同名或誤導其驗證目標，導致該測試實際沒有覆蓋它宣稱的情境。
MEDIUM：兩個同時存在於 API 表面的名稱僅有極小差異（如單複數），容易被呼叫端選錯但影響範圍可控（型別檢查/lint 能攔截大部分誤用）。

## 反例（不該報）
- 內部命名遵循專案既有縮寫慣例，且完全侷限在私有/內部模組範圍，不會外洩到公開 API 或序列化輸出。
- 兩個測試共用相同或相似名稱是刻意設計（例如同一組 fixture 的參數化測試），且各自驗證的情境與名稱語意一致，不構成誤導。
- 名稱雖然相似，但因所在的 namespace、檔案、或呼叫情境完全不同，實務上不會被混淆或誤呼叫。
