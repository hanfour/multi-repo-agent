## 觸發訊號
- diff 新增或保留的行內註解，只是把下一行（或下一段）程式碼直接翻譯成文字重述（例如 `// Reset scroll` 後面接的程式碼命名本身就已經說明這件事），完全沒有交代「為什麼」要這樣做、有什麼限制、或有什麼非顯而易見的前提。
- diff 新增三層以上的巢狀/串接三元運算子，且各層依據不同變數或條件混合判斷（例如同時判斷方向、範圍邊界、使用者傳入選項），需要逐層手動模擬才能還原邏輯，而不是一眼看穿。
- diff 中的註解描述的行為與其緊鄰程式碼的實際邏輯已經對不上（例如舊註解講的是改動前的行為；或作者事後才發現註解寫錯，用刪除線/更新文字澄清）。
- diff 移除或改寫錯誤訊息、log 文字時，新文字在語意上不再準確描述實際情境（例如把純語意錯誤描述成可以合法使用的替代方案）。

## 判準
資深 reviewer 讀 code 時，註解與程式結構應該傳遞「為什麼」而不是「是什麼」——如果拿掉這行註解，光看程式碼本身就能重建一樣的理解，這行註解就是雜訊；之後改動程式碼時很容易忘記同步更新它，久了就變成誤導後人的來源。巢狀三元運算子的問題性質類似：三元運算式本身合法、也很常見，但當多層巢狀混合不同判斷依據時，讀者無法一眼分辨每一層在回答哪個問題，必須手動追蹤執行順序才能確認行為，這種認知負擔在 review 當下、以及未來維護改動時都會拖慢速度、提高誤改風險。錯誤訊息/註解與程式碼實際語意不一致，則會直接誤導開發者做出錯誤判斷（例如把「不安全的行為」誤寫成「可以合法遷移到的替代方案」）。

## 嚴重度
CRITICAL：（此類問題屬於可讀性 / 維護性範疇，通常不會造成執行期錯誤，不會到 CRITICAL）
HIGH：錯誤訊息或 API 說明性文字語意錯誤，可能誤導使用者採取不安全或不正確的做法（例如把 side-effect 誤導成可安全移到某生命週期方法）；或巢狀三元運算子混用超過 3 種不同判斷依據，連作者本人都需重新推導才能解釋自己寫的邏輯。
MEDIUM：新增的註解只是重複程式碼字面意思、未解釋 why；或註解已與程式碼不同步、有誤導風險，但不涉及使用者會直接依賴的錯誤訊息。

## 反例（不該報）
- 註解解釋的是「為什麼」而非「是什麼」，例如引用 issue/bug 編號、說明非顯而易見的限制或副作用、或解釋一個違反直覺的執行順序（如「先取消手勢再觸發 side-effect，讓 gesture lane 能先完整 commit」）——這類註解即使旁邊程式碼看起來簡單，也不該被要求移除。
- 巢狀三元運算子只有兩層、且都是針對同一個變數的連續區間判斷（例如單純的 clamp/min-max），一眼即可讀懂，不該報。
- 為了效能考量刻意把邏輯保留在單一函式內、不抽成獨立函式（例如讓 JIT 能一次判斷完 hidden class 而非分散在多個函式各自檢查一次），這是效能取捨而非可讀性缺陷，不適用本規則。
- 移除的是純粹重複描述程式碼行為、且描述本身已過時或無實質資訊的既有註解/型別標註（例如已能由型別推導系統自行判斷、無需額外標註的情況），這是清理雜訊而非引入問題。
