## 觸發訊號
diff 中新增或修改了「手刻」的 thenable/Promise 狀態機：一個物件帶 `status`（如 `Pending/Resolved/Rejected` 或 0/1/2）欄位，程式在呼叫 `.then(onFulfill, onReject)`（或等價的 `.then(resolve, reject)`）的 callback 裡直接 mutate 這個物件的 `status`/`value`/`error` 欄位；或是圍繞一個非同步操作手動增減 pending 計數器（如 `request.pendingChunks++`、`boundary.pendingTasks--`、`abortableTasks.delete`）；或是只接了 `.then(onFulfill)` 沒有第二個 reject 參數也沒有後續 `.catch`。

## 判準
這類手刻狀態機重建了 Promise 本來就有的「只能 settle 一次」語意，但常見漏兩件事：(1) 沒有在 resolve/reject callback 一開始檢查「這個 record 是否仍是 Pending」，導致同一個 thenable 被重試、快取被重新讀取、或元件被中止後又非同步 settle 時，用過期資料覆寫較新的結果，或造成計數器被重複遞減（真實案例：`boundary.pendingTasks--` 在已經走過 `finishedTask` 路徑後又被扣一次，導致計數變負）；(2) 只處理 fulfilled 分支、沒有對稱處理 rejected 分支，一旦底層 promise reject，record 就永遠卡在 Pending，後續讀取者會不斷 re-throw 同一個永遠不會 settle 的 thenable，導致呼叫端掛住而非拿到錯誤。這些 bug 在正常路徑测试不出來，只有在 race（重試、abort、二次讀取）或錯誤路徑下才會現形，而且通常沒有任何 log 或崩潰訊號，非常隱蔽。

## 嚴重度
CRITICAL：thenable 的 reject/error 分支完全缺失（只接了 fulfill callback，沒有 onReject 也沒有 `.catch`），一旦來源 promise reject，consumer 會永遠掛在 pending 狀態，錯誤被靜默吞掉。
HIGH：resolve/reject callback 沒有先檢查 `status === Pending`（或等價的 in-flight 判斷）就直接 mutate 共享 record，或圍繞非同步操作的 pending 計數器在多條路徑（正常完成 / abort / error）下可能被重複增減，造成 use-after-free 風格的計數錯誤或資料被過期結果覆寫。
MEDIUM：reject 路徑存在但和 resolve 路徑處理不對稱（例如監聽器/timer 只在其中一支清掉、cleanup 沒有一起做），或錯誤被吞下後只是重新包一個訊息不明確的 Error，難以回溯原因。

## 反例（不該報）
直接使用原生 `await`/`Promise.then` 且不另外維護可變的 `status` 欄位——原生 Promise 本身已保證單次 settle、reject 會自然拋出，不需要額外守衛。若計數器增減都被限制在單一、無法重入的同步區塊內（例如整個生命週期只有一條路徑會呼叫且已用 try/finally 保證成對），也不算此類問題。純粹的 fire-and-forget、且操作本身冪等（reject 也不影響狀態正確性，如單純的 log 上報）不需要額外的 pending 守衛。
