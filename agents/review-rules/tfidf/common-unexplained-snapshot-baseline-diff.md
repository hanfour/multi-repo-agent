## 觸發訊號
Diff 中修改了測試的 golden/baseline/snapshot 輸出檔（例如 `tests/baselines/reference/**/*.errors.txt`、`*.types`、`*.js`、`*.d.ts`、`*.jsonc`，或任何專案的 `__snapshots__/**`、`*.snap`、user-suite `*.log` 之類機器產生的期望輸出），且：
- 輸出內容本身出現實質變化（新增/刪除錯誤訊息、型別推論結果改變、emit 出的程式碼不同、診斷代碼或訊息文字改變），
- 而 PR/commit description、程式碼註解或該筆 diff 本身都沒有說明「為什麼新的輸出才是正確的」，也看不出這是預期的行為改動還是意外的回歸。

## 判準
Golden file 測試的本質是「凍結目前行為」，diff 一旦改到它，reviewer 唯一能判斷正確性的依據就是輸出內容本身和 PR 的敘述——語言/編譯器/型別系統這類專案尤其如此，因為一行 baseline 差異背後可能是：
1. 純粹的訊息措辭調整（無害），
2. 型別系統語意正確性的改善（預期且良性），
3. 隱藏的邏輯回歸或本不該產生的錯誤（例如「這個錯誤本來就不該出現」「這其實暴露了先前遺留的 bug」的案例反覆出現在這批意見中）。
資深 reviewer 之所以逐一追問「這是對的嗎？」「這是刻意的嗎？」，是因為 snapshot diff 本身無法自證因果——沒有推理鏈就無法排除「巧合地讓測試通過」和「真的修對了」兩種情況。沒有解釋的 baseline 變動會讓後續維護者（包含未來的作者本人）失去追溯行為變更原因的依據，也讓 code review 退化成「盯著幾百行 diff 猜測」。

## 嚴重度
CRITICAL：baseline 變化顯示既有正確行為被破壞（例如型別檢查器不再報出本該報的錯誤、emit 出的程式碼在執行期語意不同、宣告檔遺漏必要匯入導致下游編譯失敗），且沒有測試新增或說明佐證這是刻意的。
HIGH：diff 讓一個原本會攔截使用者錯誤的診斷訊息消失或減少（漏報回歸），或新增的訊息明顯誤導使用者（錯誤位置、措辭不精確到會讓人採取錯誤修法），且 PR 未解釋。
MEDIUM：baseline 差異看起來良性（純措辭改善、訊息更精確），但沒有任何說明文字，需要 reviewer 額外花時間逐行推敲才能放行；或改動只影響內部診斷排序/格式而语意不變，但仍缺乏理由。

## 反例（不該報）
- PR description 或緊鄰的 commit message／程式碼註解已清楚解釋 baseline 為何改變（例如指出對應的 issue 編號、貼出修正前後語意差異的最小重現），reviewer 只是在核對細節，不代表變更本身可疑。
- 純粹新增測試案例導致 baseline 檔新增區塊（而非既有區塊的值被修改），這是預期的測試擴充，不是「未解釋的行為改變」。
- 因為重新產生 baseline 而出現的格式性差異（縮排、換行符、欄位順序）且內容語意完全相同。
- 作者本人在該筆 diff 的行內留言中已經給出因果解釋（即便解釋是在 review 討論串裡，而非 PR 主文），此時規則的訴求已被滿足。
