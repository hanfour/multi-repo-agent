## 觸發訊號
diff 對既有 public 方法/選項/預設值做了行為變更或移除，但沒有先經過棄用（deprecation）週期：例如直接 `raise` 讓原本可運作的呼叫方式報錯、直接改掉一個布林/預設參數的行為、直接刪除一個 public 方法或常數、把原本寬鬆接受的輸入型別收緊、或是把原本 silently 允許的呼叫模式變成 hard failure——而 diff 裡找不到對應的 `ActiveSupport::Deprecation.warn(...)`、`deprecate :method_name`、或至少一個過渡期的 opt-in config（例如 `config.active_record.xxx = :new_behavior`）。也包含反過來的情況：加了棄用警告，但訊息裡沒講清楚「該改用什麼」或「哪個版本會移除」。

## 判準
Rails 核心對外部使用者的承諾是「行為變更要有棄用週期」——使用者在升級 minor 版本時只會看到警告，下一個 major 版本才會真的壞掉。resident reviewer 反覆糾正兩類問題：(1) 完全沒有棄用警告就變更/移除行為，這會讓所有依賴舊行為的下游 app 在升級後直接壞掉且毫無預警；(2) 棄用警告訊息寫得不夠明確——沒講清楚新舊行為差異、沒告訴使用者要怎麼遷移、沒標註目標移除版本，這種警告等於白加。另外也常見「該不該保留舊路徑的效能優化」爭議：直接砍掉一個 fast path 換成永遠正確但較慢的寫法，也需要在 PR 裡明確討論這個 trade-off，而不是默默犧牲效能去修 bug。

## 嚴重度
CRITICAL：public 方法/常數被直接砍掉、或既有呼叫方式從「可運作」變成「拋例外」，且完全沒有 deprecation warning 或 opt-in config 做為過渡。
HIGH：有加警告，但訊息中缺少「改用什麼」或「哪個版本移除」等關鍵資訊，導致使用者看到警告也不知道該怎麼辦；或是把一個會影響大量下游行為的 default 選項改變了值卻只在 CHANGELOG 帶過一句、没有 runtime warning。
MEDIUM：警告訊息用字/格式可以更清楚（例如没有用 `<<-MSG.squish`、没有維持一致的 gem 名稱/版本號寫法），或 CHANGELOG 裡漏寫了遷移範例。

## 反例（不該報）
- 純新增的 public API（新方法、新選項、新 class），不影響既有呼叫方式。
- 只影響 `:nodoc:` 標記的內部方法、或明確標示為 private/internal 的程式碼路徑。
- 修的是一個從未按文件行為運作的 bug（即修正後才符合文件承諾的行為），這種屬於 bugfix 不屬於 breaking change。
- 變更被包在一個預設值等於舊行為的 opt-in config 之後（例如 `config.active_record.foo = false` 預設關閉新行為），使用者不主動開啟就不受影響。
- 對還沒有正式發布過的 API（例如同一個尚未 release 的版本裡新加的方法又被調整）做調整，此時沒有使用者依賴舊行為，不需要棄用週期。
