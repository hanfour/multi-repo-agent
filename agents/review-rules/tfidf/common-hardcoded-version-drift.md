## 觸發訊號
diff 中新增或修改了 CI workflow（GitHub Actions matrix、CircleCI parameters）、Dockerfile、preinstall/postinstall script、或其他建置設定裡的手寫版本字串（Node.js/pnpm/工具版本、engines 範圍、SHA pin），且符合下列任一情況：
- 專案內已存在單一版本來源（package.json 的 `engines` 或 `packageManager` 欄位），這次改動卻另外手寫一份版本字串，沒有引用既有來源。
- 同一版本號需要同步出現在多處（多個 CI job matrix、Dockerfile base image、CircleCI parameters、`engines` 欄位、preinstall 腳本裡手動解析的版本判斷），diff 只改了其中一處。
- 調整了 `@types/*` 型別套件的 semver range，卻沒有同時檢查/驗證它對應的執行期套件（例如 `pg`、`sequelize`）在常見版本組合下仍能通過型別檢查。

## 判準
版本字串手寫在多個檔案時，遲早會有一處被漏改，造成 CI 矩陣、Dockerfile、`engines` 宣告彼此不同步——這類 drift 通常要等某個環境的建置或測試失敗才會被發現，而且光看單一檔案的 diff 很難看出「這裡漏改了」。單獨調高 `@types/*` range 更隱蔽：本地 `tsc`/CI 可能是綠燈，但下游消費者用不同版本組合安裝時才會編譯失敗，是典型「本地綠燈、外部紅燈」的問題，且錯誤發生的位置（consumer 專案）跟改動位置（本專案 package.json）是分開的，難以在 review 當下靠測試發現。

## 嚴重度
CRITICAL：（不適用，此類問題本質上是維護性/相容性風險，非立即當機）
HIGH：版本不一致會破壞已發布套件對外承諾的相容性（例如調整 `@types/pg` range 未驗證跨版本組合，導致下游 consumer `tsc` 直接編譯失敗），或 `engines`/`packageManager` 宣告的最低版本與程式碼實際依賴的語言特性不符（例如程式用到只有 Node 22+ 才有的 `require()` of ESM 行為，`engines` 卻仍寫 `>=20`），造成使用者在宣告支援的版本上實際跑不動。
MEDIUM：CI matrix、Dockerfile 版本手寫重複，且沒有集中到單一來源（`engines` 或 `packageManager`），未來版本升級時容易漏改其中一處，造成 CI 涵蓋範圍與實際發布支援範圍不一致。
LOW：純粹是 CI job 顯示名稱、非功能性版本字串調整，或已有明確理由記錄在 comment/PR 描述中說明為何暫時維持手寫版本（例如刻意繼續支援已過 EOL 的版本）。

## 反例（不該報）
- 把既有的唯一來源版本號從舊值換成新值（例如 package.json 的 `"node": ">=16"` 改成 `">=18"`），且沒有其他地方需要同步——這是單純升版，不是 drift。
- 為了刻意做跨版本相容性測試，在 CI matrix 中列出多個版本（例如 `node: [18, 20, 22]`）——這是有意的矩陣測試設計，不是「重複來源」問題。
- GitHub Actions SHA pin 的例行安全性更新（bump 到最新 commit hash + tag 註解），這是既有慣例下的維護性 commit，不代表 drift。
- 在 devDependencies 加入某工具版本（如 vitest、typescript），而該套件在 monorepo 內本來就是各套件獨立管理版本、非共享單一來源，不算 drift。
- PR 描述或 review 討論中已明確說明「這裡刻意不跟其他地方同步」的理由（例如 skeleton/scratch 專案刻意排除某個 cooldown 設定），且該理由記錄在程式碼註解或 commit message 中。
