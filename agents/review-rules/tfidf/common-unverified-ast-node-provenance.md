## 觸發訊號
diff 中對一個 `Node`（或其 `.parent`）做以下任一操作，且沒有先確認該節點是「原始 parse tree 節點」還是「合成／轉換後節點」：
- 直接呼叫 `.parent` 或串接 `.parent.parent...` 來定位祖先節點、取得 enclosing declaration，卻沒有用 `nodeIsSynthesized()`、`getParseTreeNode()`、`NodeFlags.Synthesized` 或等價檢查先驗證來源
- 在尚未執行過 `bindSourceFile`／`setParentRecursively`（例如在 binder 執行前、或對剛用 factory 建出的節點）就呼叫依賴 `.parent` 或符號解析的 API（`resolveName`、`getResolvedSymbol`、`getSymbolAtLocation`）
- 用 `as SomeNode` 或 `<SomeNode>node` 做未經 runtime 驗證（無 `isXxx()` guard、無 `Debug.assert`）的窄化轉型，且轉型成立與否僅靠呼叫端的「默契」或函式命名維持
- 假設某個 helper（如 `getResolvedSymbol`）在任意語境下都安全，而它實際上只對特定語法位置（例如「特定種類的 expression-context identifier」）才正確

## 判準
Transformer／codefix／language service 產生的合成節點不保證有 `.parent` 指標，`nodeIsSynthesized()` 也不總能反映節點真正來源（例如被 `setTextRange` 處理過的節點，`nodeIsSynthesized` 會回傳 `false`，即便它是合成的）。在 bind 階段之前呼叫任何依賴 `.parent` 的 API，得到的可能是 `undefined`，也可能解析到錯誤的作用域——這類錯誤通常要到執行期、且往往是在特定轉換管線組合下才會浮現，很難靠型別系統或一般測試攔截。同理，未經驗證的 `as`/`<T>` 轉型一旦前提不成立，會在編譯器內部造成難以追蹤的崩潰或悄悄產生錯誤結果；資深 reviewer 對這類模式特別敏感，是因為已經多次看過「這段程式在 parse tree 上沒問題，換成 transformer 產生的節點就炸了」的實際事故。

## 嚴重度
CRITICAL：在 transformer、codefix 或 language service 的主路徑上，對可能是合成節點或尚未綁定的節點呼叫依賴 `.parent`／符號解析的 API，且沒有任何 fallback 或防禦性檢查，可能導致空指標崩潰或使用者可見功能（rename、go-to-definition、診斷）直接壞掉
HIGH：在 checker 或 binder 的核心路徑中使用未經驗證的 `as`/`<T>` 轉型，前提只靠註解或呼叫慣例維持，未來重構很容易違反前提而產生靜默錯誤
MEDIUM：局部工具函式或測試輔助程式碼中依賴 `.parent` 卻未加檢查，但影響範圍小、下游有其他檢查兜底，或該函式明確只在保證 parent 已設置的場景（例如已完成 checker 全量走訪之後）被呼叫

## 反例（不該報）
- 存取 `.parent` 的節點確定來自原始語法樹，且此時已完成 `setParentRecursively`／`bindSourceFile`（例如語意檢查階段的一般節點走訪）
- 轉型前已用 `isXxx()` type guard 或 `Debug.assert()` 實際驗證過節點種類，`as` 只是補足型別系統推斷不出的部分（這是合理、安全的窄化，不是「憑默契」的轉型）
- 呼叫前已明確用 `NodeFlags.Synthesized`、`nodeIsSynthesized()` 或 `getParseTreeNode()` 檢查過節點來源，才進一步存取 `.parent` 或做符號解析
